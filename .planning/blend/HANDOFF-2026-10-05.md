## How Spotify reaches the phone

1. A signed-in account presses Connect. `POST /api/spotify/connect` saves an expiring hashed state
   and PKCE verifier, then returns the Spotify authorization URL.
2. Spotify returns to `/api/spotify/callback`. The API consumes the one-use state, exchanges the
   authorization code, reads the Spotify account and stores encrypted access/refresh credentials.
   Public replies contain connection state and playlist metadata, never credentials.
3. `GET /api/spotify/playlists` lists the available source playlists. Development-mode access can
   reject playlists the listener does not own or collaborate on; this must be shown clearly.
4. `POST /api/spotify/sync` processes a source page of up to 50 rows. Receipts skip Spotify track
   IDs already transferred. The matcher finds catalog recordings; exact matches are added through
   `auth.library.apply`, with `origin: 'import'`. Uncertain/unavailable matches remain unreceipted
   for a future scan. The API returns cumulative counts for that scan: clients must not sum them.
5. After acknowledged library writes, the Spotify store commits receipts and its scan checkpoint.
   Manual sync repeats bounded steps until completion. It adds new songs and preserves local edits;
   it does not mirror Spotify removals or download Spotify audio.
6. These are ordinary Convex library rows. LuvLyrics, signed into the same Allegra account and
   Convex deployment, reads the revision feed into its online library/SQLite sync layer. Spotify
   need not be connected separately on each device.
7. With Daily enabled, `convex/crons.ts` schedules `spotifyCron.scheduleDaily` every 24 hours.
   Per-account durable actions call the authenticated API internal hook. Each API call has a
   45-second budget; `{ more: true }` requests a scheduled continuation, capped by the cron code.
   Only previously selected/tracked playlists are eligible. There is no phone background timer.

## First fixes before calling the workflow complete

**Confirmed contract defect — Spotify destination playlist IDs.**
`apps/api/src/services/spotifyTransfer.ts` currently constructs `spotify:<sourceId>`.
`packages/shared/library.ts` rejects `:` in a playlist ID. A direct current-checkout reproduction:

```text
parseLibraryOps([{ op: 'playlist_upsert', playlistId: 'spotify:pl0000000001',
                  name: 'Road', isPublic: false, at: 1 }]) -> null
same operation with playlistId 'spotify-pl0000000001' -> accepted
```

The transfer writes directly to the library store and its test fake accepts every typed operation,
so initial transfer can bypass the parser while later device edits fail. Fix this as a vertical
slice: safe ID creation, a parser-backed transfer test, and an additive migration for any existing
playlist metadata/items, Spotify tracked destinations and receipts. Preserve edits/tombstones and
avoid creating a second playlist when a source was already imported. Do not just change the prefix.

**Remaining Spotify review, based on current source; not reproduced account exploits:**

- `refreshAccessToken` saves an earlier connection object; `convex/spotify.saveConnection` can
  insert unconditionally. Test a refresh/callback completing after disconnect or account erasure,
  and settings changed during refresh. Add durable generation/CAS fencing and account-existence
  checks if late work can restore credentials or overwrite Daily.
- Refresh deduplication is an in-process `Map`. Test two serverless instances refreshing a rotated
  token concurrently; use a durable refresh claim/version rather than assuming one process.
- OAuth state is hashed, expiring and one-use, but the callback consumes a query state without a
  separate initiating-browser proof. Audit cross-browser/account-linking CSRF and cancellation/
  expiry/mobile return paths before declaring the connection safe.
- `dailyStep` does not recheck `dailyEnabled` before each queued step. Test switching Daily off
  while a previously scheduled action is pending or running.
- `dailyStep` catches playlist errors, so the API can return success even for a provider 429/5xx;
  the outer Convex retry branch cannot then observe that error. Preserve a resumable cursor and
  meaningful retry/backoff status rather than silently waiting until the next day.
- Daily processing currently takes the first five enabled playlists; scheduling takes 100
  accounts. Test larger sets for starvation and add fair persisted pagination if needed.
- A finished checkpoint resets stored scan counters. Verify what the status panel should show
  after completion, reload and another device's sync; distinguish last-result counts from active
  scan counts and retries.

**Other acceptance still open:** one real Spotify export fixture; low-memory ZIP import on a

Android's manifest currently registers the `lyricflow` scheme; a parsed HTTPS invite alone does
