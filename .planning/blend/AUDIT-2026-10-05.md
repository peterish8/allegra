## Backend, consistency, privacy, and operational limits

### F01 — P0 — A stale builder can overwrite a membership or learning change [R, S, G]

**Evidence:** PLAN B2/B4; `08-01-PLAN.md:104`; `convex/blends.ts:84`, `:251`, `:297`, `:328`;
`apps/api/src/user/blendStore.ts:223`. Only `saveBuild` increments `buildVersion`; join, leave,
and `setLearning` merely set `stale=true`. R1 and R2 demonstrate the gap.

**Failure:** a build reads A+B, B leaves or disables learning, and that old build still saves and
sets `stale=false`. The new membership is displayed beside the old tracks and scores.

**Revision:** introduce an input revision that changes with membership and privacy settings.
Capture and compare it at publication, together with the build revision. Validate every pair,
track attribution, gift, and story against that membership snapshot. Do not rely on a boolean.
Convex transactions protect one mutation, not the multi-request read/provider-work/save sequence.
[Convex OCC documentation](https://docs.convex.dev/database/advanced/occ).

**Acceptance:** pause a build before save, independently join/leave/disable learning, then release
it. Every obsolete save loses; the next response uses the new membership and settings. Repeat
with a six-member group and an account erase.

### F02 — P0 — Privacy withdrawal uses best-effort cleanup and stale settings [S, G]

**Evidence:** `03-03-PLAN.md:100`, `08-04-PLAN.md:58`;
`apps/api/src/routes/user.ts:249` catches failures from tally clear and membership updates;
`apps/api/src/services/blendBuild.ts:223` trusts the membership's learning snapshot;
`convex/taste.ts:147` does not check the current profile preference.

**Failure:** settings save successfully while cleanup or `setLearning` fails. Subsequent builds
can continue using the tally until another switch succeeds. A listen request authorized before
the switch can also write its tally after learned profile data was cleared.

**Revision:** enforce the current privacy preference/epoch in the transaction accepting a tally
write and in the build publication guard. Make cleanup durable, observable, and retryable;
failed cleanup must not authorize continued use. Apply the same fence to account erasure.

**Acceptance:** inject failure into each cleanup step, race an in-flight listen/build with the
switch, retry without toggling again, and prove no learned data is used or recreated after withdrawal.

### F03 — P1 — Departed-member data survives in stored and fallback builds [R, S, G]

**Evidence:** `convex/blends.ts:96` preserves tracks/pairs/gifts; builder `detailFor:103` falls back
to stored data and `shape:320` returns it. PLAN privacy copy allows removal at the next refresh.

**Failure:** after someone leaves, remaining members can receive previous tracks, pair scores,
gift cards, and attribution about them when a rebuild fails. `previousPairs` can retain them too.

**Revision:** specify the stronger privacy boundary explicitly: membership revocation immediately
invalidates personal build output. Suppress obsolete stories/attribution until a valid replacement
is available; safely retain independently shared songs only under an explicit rule. Purge obsolete
stored personal references. Update the leave and privacy copy to match the chosen behavior.

**Acceptance:** leave/erase while provider or database reads fail; remaining members receive no
departed-member stories or identifiers. Do not promise recall of PNGs already exported by users.

### F04 — P1 — The build deadline does not cover all work or cancel unfinished work [R, S, G]

**Evidence:** `08-03-PLAN.md:106`; builder `:76`, `:139`, `:147`, `:174`, `:204`.
Base reads and save are outside the deadline wrapper. Arguments such as `within(left(), work(), [])`
start work before the wrapper can reject an expired budget. `Promise.race` leaves work running.

**Revision:** use one propagated deadline/cancellation signal; do not start optional work after
expiry. Bound base reads and publication separately, stop queued searches, and prevent late tasks
from mutating data used by the published build. Specify whether the 3 s budget covers facts plus
discovery together, as PLAN says, or facts alone, as the draft effectively implements.

**Acceptance:** hang each dependency separately; total response time remains bounded, no more
queued searches start after cancellation, and late completions cannot alter the output.

### F05 — P1 — Database outages can become an empty "successful" daily build [S, G]

**Evidence:** builder `load:223` catches tally/likes/items failures as `[]`, then saves and marks
the result current. The provider-outage test does not test failed primary data reads.

**Failure:** a temporary library/tally outage is mistaken for an empty library. Recovery later
that day does not rebuild because `builtFor=today` and `stale=false`.

**Revision:** distinguish authoritative empty data from unavailable input. Preserve the last valid
build for non-privacy failures, mark it stale with a refresh error, and permit bounded retries.
A genuinely new Blend can show a temporary-unavailable state without storing a definitive empty build.

**Acceptance:** fail one member's primary read, recover in the same UTC day, and verify a new build
occurs. Apply F03's privacy rules before displaying a previous build.

### F06 — P1 — Compare-and-set prevents duplicate saves, not a build stampede [S, G]

**Evidence:** PLAN §7 cost estimates; `08-03-PLAN.md:102`. Every simultaneous open performs the
reads and provider work before the losing save is rejected.

**Revision:** claim a short durable build lease for one input revision/day, with expiry and owner
token. Other requests serve an allowed previous build or a refreshing state. Keep all work within
the request or an explicitly durable job; a Vercel process-local lock is insufficient.

**Acceptance:** 20 simultaneous opens cause one expensive build; a crashed builder's lease expires;
membership changes invalidate its publication; callers are never left waiting indefinitely.

### F07 — P1 — Waiting, active, and one-member-after-leave Blends are conflated [S, G]

**Evidence:** PLAN D7; `08-01-PLAN.md:113`; `convex/blends.ts:353` sweeps one-member Blends using
their original `createdAt`; the builder also accepts one-member input.

**Failure:** a months-old active pair becomes one member after a leave, receives a fresh invite,
then the next sweep deletes it immediately. A creator can also get a personal playlist/reveal
before a second person joins.

**Revision:** define `waiting`, `ready`, `refreshing`, `not_enough`, and ended behavior. Use a
waiting deadline based on the transition into waiting and the invite policy, not original creation.
Do not generate a two-person score/reveal for one member.

**Acceptance:** leave an old Blend, regenerate its invite, run the sweep, and successfully join
before the new deadline; a never-joined Blend expires as specified.

### F08 — P1 — Fifty invite-history rows can hide the live invite [S, G]

**Evidence:** `convex/blends.ts:104`, `:201`, `:74` use `take(50)` on all invite rows, while each
regeneration inserts another row and the daily sweep is later.

**Revision:** make the active invite directly addressable, or query an index that finds the newest
live invite. Bound and trim revoked history transactionally; define how long an expired code can
still produce `expired` instead of generic `notfound`. Delete all dependent rows safely.

**Acceptance:** regenerate more than 50 times before a sweep; exactly one link remains valid,
lookup returns that link, old links cannot join, and final leave leaves no orphan invites.

### F09 — Closed — Owner identity and rename authorization are implemented [V]

**Correction:** the earlier claim that the current contract lacks owner identity was incorrect.
`docs/api-contract.md` includes `ownerId`; `packages/shared/blendView.ts:47-59` carries it;
`apps/web/src/components/blend/BlendPage.tsx` uses it for the rename affordance, and
`convex/blends.ts:267-275` enforces owner-only rename. The independent backend worker checked
the contract, type, client, and server together. This is not an open defect or a required API change.

**Regression acceptance:** owner leaves; the next owner receives the edit affordance, other
members do not, and a forged rename remains rejected. Preserve the existing server guard.

### F10 — P2 — Convex return validation and the trusted gateway exception need an explicit contract [S, G]

**Evidence:** new functions in `convex/blends.ts` and `convex/taste.ts` omit `returns` validators.
Local generated guidance forbids caller-supplied authorization IDs, while these plans deliberately
follow the established secret-guarded Express gateway pattern.

**Revision:** add return validators and enforce numeric/string/array/domain caps at the Convex
boundary. Document or resolve the trusted-server exception against the local guidance. Keep the
secret server-only; derive IDs from the authenticated API principal, never the HTTP body.
The existing `requireSecret` guards mean this is not a finding of unauthenticated public access.

**Acceptance:** missing/wrong secret, a forged HTTP user ID, oversized gifts/glue, malformed scores,
and invalid refs are rejected. Valid bounded outputs satisfy their return validators.

### F11 — P1 — Private-response caching and account switches are unspecified [S, G]

**Evidence:** Blend routes set no explicit private cache policy; the plan does not define account
scoping for fetched detail, reveal markers, or import progress. This is a missing guarantee, not
proof of a present CDN leak.

**Revision:** private authenticated endpoints use an explicit `Cache-Control: no-store` policy.
Key client data by authenticated account, clear on sign-out/account change, and cancel old responses.
Invite previews need a separate bounded policy and referrer/log redaction for invite codes.

**Acceptance:** load as A, switch to B with requests in flight, and verify no A data renders;
inspect response headers and browser back/forward behavior after sign-out.

### F12 — P1 — Per-IP, process-local limits do not bound expensive work across instances [S, G]

**Evidence:** `app.ts:249` uses the default express-rate-limit store; I3 promises 30 import
requests/minute/IP and limits only four searches per individual request.

**Failure:** multiple requests/functions multiply provider concurrency; people behind a college
or household IP also share one quota. Ten thousand tracks require 200 match requests even before retries.

**Revision:** specify durable account quotas, a shared provider-work limit and a separate IP abuse
cap. Reuse the existing Convex architecture rather than provisioning a new service just for this.
Do not describe the process-local limiter as a strict global guarantee.

**Acceptance:** concurrent requests across two simulated instances respect the account/provider
budget, while two legitimate accounts behind one IP can complete with clear retry feedback.

## Taste signals and identity

### F13 — P1 — Cold seeding does not reverse likes correctly or avoid double-counting [R, S, G]

**Evidence:** `convex/taste.ts:209` and `tasteTally.ts:seed` add +10 without setting `likeBonus`
or `likeBonusAt`. R3 leaves the bonus after unlike. Seeding after live signals can add them again.

**Revision:** treat seeded likes as the same reversible contribution as native likes. Reconcile
existing rows/bonuses/recorded recent events rather than blindly adding all seed inputs. Mark the
seed done only after authoritative input was loaded; a swallowed read failure must remain retryable.

**Acceptance:** seed→unlike, live-like→seed→unlike, live-listen→seed, duplicate playlist entries,
and failed seed-read→retry all preserve exactly the intended contributions.

### F14 — P1 — Timestamp-only idempotency has a short and unstable window [R, S, G]

**Evidence:** PLAN §4.3; `convex/taste.ts:151` clamps time and keeps eight timestamps. R4/R5
recount the same event. Row eviction/deletion also erases its dedupe memory.

**Revision:** define a stable playback-session ID and cumulative listened duration; only unseen
duration can add weight, capped at one play. Use bounded device sequence/checkpoint information
and document retry/reorder horizons without adding an unbounded per-listen archive. Keep event
identity independent of clock correction. Decide how a first 5-second signal and a later
120-second signal for the same session are reconciled.

**Acceptance:** retry after nine plays, retry after eviction, future/past clock skew, two devices,
out-of-order delivery, partial/cumulative signals, and repeat-one loops all have defined results.

### F15 — P1 — Import protection and native signals differ by transport [R, S, G]

**Evidence:** `03-03-PLAN.md:83` leaves `applyFromDevice` untouched; current
`actions.ts:245` teaches Quick Picks for imported likes and `:246` for all playlist adds.
R6 adds 100 signals rather than only the planned bounded artist seed. The sync path deliberately
does not apply native tally bonuses, so mobile native likes/adds differ from web actions too.

**Revision:** make origin-aware, accepted-new-operation processing common to both transports.
Imported changes feed neither per-song tally bonuses nor per-song Quick Picks lessons. Native
mobile changes receive the same reversible contributions as native web changes. Handle import
playlist provenance for items and preserve provenance through older-client metadata updates.

**Acceptance:** 900 imported likes plus playlists cause only the bounded seed; equivalent mobile
and web native actions produce equivalent tally changes; retries/superseded ops teach nothing extra.

### F16 — P1 — Decay alone neither retires rows nor reduces an inactive Now layer [R, S, G]

**Evidence:** PLAN D2, §4.4, T5; `blendTaste.ts:45` bases beta on song count, not recency/weight.
All Now weights share the same decay factor, which cancels during normalization. R10 shows a
year of inactivity changes essentially nothing. No idle-row retirement is specified.

**Revision:** define a meaningful recency/absolute-weight floor and an eligibility window, and
base Now confidence/beta on recent evidence. Prune obsolete tally rows with a bounded mechanism
or lazy cleanup. Until retirement is implemented, remove the unconditional privacy promise that
an unplayed song "drops off". Changing the fixed landmark is not the fix.

**Acceptance:** an inactive listener's Now influence falls over 45/90/365 days, while a new play
restores influence; obsolete rows are removed within the documented retention behavior.

### F17 — P1 — One text identity conflates recordings, credits, and artist names [R, S, G]

**Evidence:** PLAN calls identity title+lead artist; `identity.ts:8` instead sorts all artist
words and removes every bracketed title segment. R8 demonstrates collisions and missed matches.
The splitter treats `Simon & Garfunkel` as separate artists; accents/Unicode forms and aliases
also need explicit policy.

**Revision:** distinguish recording identity, fuzzy cross-provider matching identity, and credited
artist identity. Preserve structured lead/featured credits and meaningful live/acoustic/version
metadata. Add Unicode normalization and alias handling without transliterating distinct names
into the same identity. Keep provider ref identity for library rows and recent history.

**Acceptance:** same lead/different featured credit, reordered actual credits, reversed words in
different artist names, duo names containing `&`, Indic text, composed/decomposed accents,
live/studio/acoustic/remaster variants, and same-title covers have deliberate outcomes.

### F18 — P2 — "Minutes heard" currently includes declared bonuses and weak skip evidence [S, G]

**Evidence:** D3/D6 mix +10 likes, +5 playlist adds, and +3 recents into the tally, while export
labels the resulting score `minutes`. Playlist remove has no reversing bonus; repeating additions
can inflate it. The mobile outbox omits durations below five seconds, while D3 says skips under ten.

**Revision:** separate heard minutes from declared affinity, or rename exported values to weighted
affinity. Define one playlist-membership contribution and its removal/retry behavior. Specify
which skips count: user skip versus failure to buffer, remote handover, page closure, or a preview.

**Acceptance:** add/remove/re-add and add-to-multiple-playlists cannot manufacture listening
minutes; a stream failure is not a negative preference; genuinely short user skips follow the contract.

## Import reliability and matching

### F19 — P1 — Chunk size is measured in characters, not UTF-8 bytes [R, S, G]

**Evidence:** `05-04-PLAN.md:74` uses `JSON.stringify(...).length`; API limit is 32 KB. R7 proves
the mismatch with Devanagari text. A valid import can repeatedly fail with 413.
Current `packages/shared/importPlan.ts:21,59` also measures characters, while
`apps/web/src/lib/api.ts:378` adds `sentAt` to the serialized request envelope.

**Revision:** measure the fully serialized envelope using `TextEncoder`/UTF-8 byte length,
including `sentAt`, punctuation and metadata. Split before 28 KB; handle an individually oversized
op explicitly. Keep the op-count limit too. Update the cost table's incorrect "1,000 songs in 5
requests": 100-op chunks require at least ten, and the byte limit can require more.

**Acceptance:** long Hindi/Tamil titles, emoji, album/artwork URLs, and envelope overhead never
produce a request above the byte limit; a 413 is actionable rather than an endless retry.

### F20 — P1 — ZIP guards omit total decoded bytes and memory/time budgets [S, G]

**Evidence:** I2 and `05-02-PLAN.md:66` cap compressed archive and individual declared sizes.
Many individually valid entries can still expand to gigabytes, before the 10,000-track parser cap.
Current `apps/web/src/lib/importFile.ts:42-60,68-78` uses synchronous `unzipSync` and also lacks
an aggregate expanded-byte/work limit. A worker protects the UI thread, but not process memory.

**Revision:** cap wanted-entry count, aggregate declared and actual decompressed bytes, and parse
time/memory. Bound hashing/copies; prefer incremental inflation with output accounting and
termination. Handle corrupt/truncated archives, missing size metadata, duplicate basenames,
unsupported compression and encrypted entries. Do not inflate unwanted content.
These are local-device risks because the ZIP is not uploaded. The mitigation follows
[OWASP's decompressed-size guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
and [fflate's streaming/metadata API](https://github.com/101arrowz/fflate).

**Acceptance:** many 19 MB wanted entries, false/missing declared sizes, high compression ratio,
corrupt files and huge junk content stop within a measured memory/time budget; playback remains responsive.

### F21 — P1 — Resume only checkpoints matches, not an import transaction [S, G]

**Evidence:** `05-03-PLAN.md:84` stores `[fileHash, trackKey]`; saving only keeps counters in
reducer state. No persisted accepted selections, manual replacements, stable op timestamps, chunk
acks, or save position is specified.
The current `apps/web/src/lib/importProgressStore.ts:11-22,38-85` persists matches keyed by file
hash, while `apps/web/src/lib/importReducer.ts:22-38` keeps selection/review state in memory.
Current resume requires selecting the same file again and skips matching; it does not restore
review choices or a partially accepted save transaction.

**Revision:** persist an account-scoped, versioned import manifest covering preview selection,
match results, review decisions, planned ops and save receipts. Keep op identity/time stable over
reload. Reconcile accepted/rejected/superseded library ops before calling a chunk complete. Set
a retention TTL, a cancel-and-forget action, and clear account data on sign-out/erasure.

**Acceptance:** close after the server accepts a chunk but before the reply, reload mid-save,
switch account, change parser/matcher version, and exhaust storage quota without duplicate writes
or mistaken success. If storage is unavailable, say resume is unavailable; do not promise it silently.

### F22 — P1 — Playlist name is not a playlist identifier [S, G]

**Evidence:** I4 and `05-04-PLAN.md:67` hash only `source + name`; selected playlists are also
keyed by name. Two playlists named "Focus" become one, and renaming changes the ID.
Current `packages/shared/importParse.ts:14-25,138-180` models playlists by name, and
`packages/shared/importPlan.ts:27-29,50` derives IDs from source and name.

**Revision:** preserve a stable source playlist ID/URI when available, or use an explicit manifest
mapping that distinguishes same-name playlists. Define re-import as append, reconcile, or replace,
and protect user edits. Define ordering/repeated-track handling because set-style library items
cannot preserve every Spotify playlist's repetitions or source sequence automatically.

**Acceptance:** two same-name lists, rename, reordered export entries, edited lists, repeated songs,
and re-import of a later export behave as the selected product policy specifies.

### F23 — P1 — Saving errors lose the context needed by "Carry on" [S, G]

**Evidence:** `05-01-PLAN.md:102` error state has only message/kind/resumable, and `:120`
allows error→choose only. `05-03-PLAN.md:92` promises restarting matching; saving failures need
their own resume point. Late worker/network messages have no run ID in the planned actions.
The current reducer preserves a preview resume payload for matching errors
(`apps/web/src/lib/importReducer.ts:102-104`), but saving errors set `resumable:true` without a
resume payload (`:115-121`). `apps/web/src/components/import/ImportPage.tsx:284` shows "Carry on"
only when both exist. The save-failure copy therefore promises recovery that is not actionable.

**Revision:** keep the durable manifest/run ID separate from the screen state. Specify transitions
for paused, retrying and partially saved imports, and ignore responses from obsolete runs. Abort
workers/fetches and abort-aware retry waits on cancel, account switch and unmount.

**Acceptance:** pause→resume works in matching and saving; choose file B while file A completes;
cancel during Retry-After; double-submit; late results never enter the newer run.
For a saving failure, assert that a visible recovery action restores the acknowledged save
position and retained review choices, not merely that the reducer contains a resumable boolean.

### F24 — P1 — Provider unavailability is indistinguishable from "not found" [S, G]

**Evidence:** matcher `importMatch.ts:133` returns `confidence:'none'` after a provider failure;
the plan stores completed match results in IndexedDB. The current matcher avoids caching thrown
provider failures on the server, but the client can still treat them as final.

**Revision:** add an explicit transient/unavailable outcome or separate retryability field. Do not
checkpoint provider failure as a definitive catalog miss. Retry with bounded backoff and jitter;
handle both delta-seconds and date-form Retry-After. Add a total deadline for a 50-track match
request, not only individual provider timeouts.

**Acceptance:** outage→reload→provider recovery rematches affected tracks; true misses can be
skipped; cancellation and 401/403 have distinct recovery from 429/5xx.

### F25 — P1 — Variant ambiguity and cache keys can preserve wrong matches [S, G]

**Evidence:** matcher normalizes trailers and ranks by exact/close plus provider order, uses no
album in its cache key, and permits `close` despite duration mismatch. `close` is preselected in
`05-01-PLAN.md:121` and `05-04-PLAN.md:94`.

**Revision:** preserve album/version/structured artist evidence and ranking margin. Expose multiple
candidate choices when ambiguous; include matcher version and relevant disambiguating metadata
in cache keys. Require a deliberate decision for ambiguous matches, with a bulk choice if desired.
Do not equate a Saavn ref with proven playable media; define later unavailable-track handling.

**Acceptance:** live/studio, explicit/clean, cover/original, same title by two artists, remaster,
different albums and different durations do not silently import the wrong recording.

### F26 — P1 — Real Spotify-format compatibility remains unverified [S, G]

**Evidence:** `04-01-SUMMARY.md` and the fixture README explicitly call the data synthetic;
REQUIREMENTS IMP-01 requires a real reduced export. The summary reports prior approval for
synthetic fixtures; that approval does not establish current Spotify format compatibility.

**Revision:** retain synthetic fixtures but make real-format verification a distinct release gate.
Verify filenames, nesting, library item types, playlists, encoding and optional URI/date fields
against an authorized anonymized export. Do not guess a schema from a support article.
[Spotify describes the categories and available metadata, not these exact JSON keys](https://support.spotify.com/us/article/understanding-your-data/).

**Acceptance:** an actual current export imports; podcasts/local files are correctly excluded;
separate JSON files can be combined without overwriting previous selection; CSV dialects, quoted
newlines, malformed quoting, BOM, duration units and truncation accounting have fixtures.

## Matching, stories, fairness, and cold start

### F27 — P2 — Confidence and percentage copy overstate what was validated [S, G]

**Evidence:** §4.6 uses effective sample size; §8.3 says "fewer than 20 items". With uniform
weights, lambda reaches 0.6 at 12 songs; a concentrated 200-song input can still have low confidence.
Synthetic outcomes do not calibrate "you'd enjoy 74%" as a real prediction.

**Revision:** choose one confidence contract based on effective evidence, recency, and data
coverage. Use estimated compatibility wording. Add real-listener calibration and checks for
different languages, imported-heavy libraries and highly concentrated taste before making
accuracy claims; do not retune only to the simulation.

**Acceptance:** 3/12/20/200 uniform and concentrated inputs yield intentional labels; missing
facts lower confidence; no NaN/out-of-range output; held-out feedback measures the chosen outcome.

### F28 — P2 — Stories can invent the cause of a score change [S, G]

**Evidence:** `blendMatch.ts:explainChange` reads the top ten contributions from only one ordered
user side and chooses the largest absolute change. Copy says "you both played more" even when
imports, likes, normalization, confidence, or recovered artist facts caused the movement.
"Hasn't heard" cannot be known from bounded taste membership either.

**Revision:** store sufficient symmetric contribution/provenance summaries or use cautious copy
without causal claims. Distinguish preference change from metadata/algorithm/confidence change.
Version facts and algorithm, record missing-fact coverage, and avoid describing a missing item in
the bounded tally as proof of never listening. Prefer song-level language over one majority
language per multilingual artist where available.

**Acceptance:** only B changes, an artist moves outside top ten, facts recover, or an import arrives;
the explanation stays true. Library-only members are never described as having listened more.

### F29 — P2 — Fairness, spacing and daily novelty are not universally compatible [S, G]

**Evidence:** BLD-02 requires ten changed positions every day even for a tiny/single-artist pool;
§4.7 starts with a soft spacing penalty but demands a hard spacing fixture. The builder summary
implemented a stronger exclusion rule. Nash welfare alone is not a guarantee of a 0.05 utility gap.

**Revision:** define hard constraints versus preferences and a fallback order for infeasible pools.
Condition novelty on enough alternatives. Preserve the synthetic fairness tests, but add adversarial
and randomized tests and measure per-member utility/coverage, rather than promise equality for all inputs.
[Spotify's engineering write-up presents relevance, coherence, equality and democracy as competing objectives](https://engineering.atspotify.com/2021/12/a-look-behind-blend-the-personalized-playlist-for-youand-you).

**Acceptance:** 1/9/10/50 candidates, one dominant artist, no overlap, one empty member, five similar
plus one outlier, adversarial weights and identical seeds all terminate with deliberate fallbacks.

### F30 — P1 — Disjoint or empty tastes have no discovery source [R, S, G]

**Evidence:** builder `discovery:262` uses only songs held by at least two members. R9 records
zero suggestions for disjoint tastes. The pure builder's thin-member test supplies discovery
externally, so it does not prove orchestration can obtain it.

**Revision:** define fallback seeds from each member's top playable songs or explicit onboarding
picks within the same budget. Treat an entirely empty member as needing input, not as fabricated
personalization. Keep unresolved/unplayable tracks out of selection and clearly count them.

**Acceptance:** disjoint-language pair, one empty member and entirely Gaana-only/unresolved inputs
each produce the intended list or actionable empty state, without an invented match/story.

## Web interaction, playback, and accessibility

### F31 — P1 — Invite polling overlaps expensive builds and hides persistent errors [S, G]

**Evidence:** `09-02-PLAN.md:63` calls full detail with `setInterval(3000)` while a build can take
8 s; errors are ignored. The stated ten-minute wait produces up to 200 polling requests.
Current `apps/web/src/components/blend/BlendInviteSheet.tsx:39-61` implements that interval;
closing clears the timer but does not cancel its in-flight request.

**Revision:** poll a cheap membership/status response, use completion-based scheduling with one
request in flight, abort on close/unmount, pause when hidden, and back off on 429/network failure.
Surface revoked/full/ended/auth-expired states. Fetch/build full detail only when needed.

**Acceptance:** slow 8 s response, ten-minute wait, hidden tab, account switch, revoked link and
rate limiting never overlap polls or continue work after close.

### F32 — P2 — Queue semantics need integration acceptance alongside the existing playback router [G]

**Evidence:** WEB-05 and `09-04-PLAN.md` mention the funnel, while the architecture requires picks
to route to the authenticated account's active Connect device and preserve queue semantics.
The current Blend page already receives `App.playSong` (`apps/web/src/App.tsx:1388`), which
tries `connect.playRemote(song, queue)` before local playback (`:1008-1038`). This is not a
current Blend-local setter bypass. Mobile calls `StreamService.play(songs,index)`
(`apps/mobile/src/screens/BlendScreen.tsx:149-168`); native queue behavior still needs device proof.

**Revision:** preserve the existing app-level pick/queue router and specify its Blend acceptance.
Define row-tap queue start, filtered-view behavior, play-next/add, repeat/shuffle, unavailable songs
and a rebuild while playing. A shared Blend playlist must not create cross-account Connect control.

**Acceptance:** tap C in [A,B,C,D] → play C with the intended upcoming tail; remote device owner
receives the command; refresh/filter/navigation/leave does not reset active playback. Prove the
layout-owned audio node survives, seeking still gets 206, and Android follows the native queue path.

### F33 — P1 — Canvas generation can consume Web Share activation or fail export [S, G]

**Evidence:** `09-05-PLAN.md:57` fetches artwork before producing a blob and sharing. Browser
share needs transient user activation; `crossOrigin` alone does not grant canvas readback.
Current `apps/web/src/components/blend/shareCard.ts:14-26,97-129` awaits artwork and `toBlob`
before sharing, and downloads after every share rejection, including user cancellation.
[MDN share requirements](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share),
[MDN canvas CORS rules](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image).

**Revision:** prepare the export before the share tap, or use a two-step preview then share.
Check `canShare`, handle unsupported/blocked sharing, distinguish user cancellation from failure,
and avoid downloading automatically after cancellation. Recover from SecurityError/null blobs,
wait for fonts, support long/RTL/Indic text and emoji, and revoke download object URLs.

**Acceptance:** CORS-blocked cover, offline cover, delayed font/image, unsupported file sharing,
user cancel and small-memory mobile browser all yield a useful preview/download path.

### F34 — P1 — Keyboard semantics and long-list behavior need more than reachable controls [S, G]

**Evidence:** W7; `09-04-PLAN.md:58` says radiogroup but does not define radio state/navigation;
`11-02-PLAN.md` makes thin lines interactive; review can contain thousands of rows/search inputs.
Current `apps/web/src/components/blend/BlendPage.tsx:157-161` supplies radio roles without
arrow-key/roving-focus behavior; `BlendRing.tsx:51-68` has pair hit targets but no linear score list.

**Revision:** specify roles, accessible names, selected state, arrow-key behavior and focus return;
keep story action buttons separate from card containers to avoid nested buttons. Provide a normal
list of pair scores as an alternative to the ring. Bound rendered review rows, retain focus during
virtualization, and use batch-level progress announcements. Test zoom, large type, keyboard and
screen readers while preserving Allegra's design tokens and reduced motion.
[W3C radio-group guidance](https://www.w3.org/WAI/ARIA/apg/patterns/radio/).

**Acceptance:** keyboard-only create/join/review/share/leave, 200% zoom, 10,000-track review,
six-member ring, duplicate/long display names, reduced motion and screen-reader announcements work.
Follow repo viewports 360/768/1280/1920 rather than only the three in W6.

### F35 — P1 — Reveal identity, feature flags and older clients need a versioned rollout [G]

**Evidence:** W3 keys reveal by ID+day although a same-day membership rebuild changes the build;
web/API flags are separate; groups raise a shared cap; route plans sometimes redirect disabled
features to Home although the spec says not-found.
The installed-APK failure is not reproduced here; capability/rollback behavior is a release gate,
not evidence that a deployed old client has already failed.

**Revision:** expose build/input/algorithm versions and key reveal state by account+build identity.
Use UTC from the server for "today" and distinguish stale/refreshing from updated. Add a low-cost
shader fallback, visibility pause, cleanup, and focus handling. Define server feature capabilities
for installed APKs and enforce the same disabled-route behavior across plans/contract.

**Acceptance:** same-day join, UTC midnight at 05:30 IST, account switch, WebGL/context failure,
API-on/web-off and the reverse, old APK reading a six-member Blend, and feature rollback work.

## Additional findings from the two-worker review

### F41 — P1 — Retrying creation after a lost response creates a duplicate Blend [S, G]

**Evidence:** `apps/web/src/lib/api.ts:523-524` sends name and consent without an operation key;
`apps/api/src/routes/blends.ts:112-122` invokes creation on every request;
`convex/blends.ts:124-152` inserts a new Blend, membership, and invite for every valid call.
PLAN B2/B3 does not specify a creation retry contract.

**Failure:** the server commits but the 201 response is lost. Retrying creates a second Blend and
invite, consumes another slot in the 20-Blend cap, and can leave an abandoned link circulating.
Disabling a button during the request does not resolve an unknown commit outcome.

**Revision:** propose a client-generated creation operation key and a bounded, unique per-account
operation result stored atomically with creation in Convex. Sequential or concurrent replay returns
the original result. Define expiry and behavior if the original Blend was subsequently deleted.
Keep this within the existing Convex architecture and update the API contract before both clients.

**Acceptance:** commit creation, drop the reply, retry the same key sequentially and concurrently:
one Blend/member/invite exists and the same result returns. A different key creates another Blend.
Current join is already idempotent (`convex/blends.ts:238-239`); do not invent a duplicate-join bug.

### F42 — P2 — Account erasure leaves a stable user ID on a surviving invite [S, G]

**Evidence:** invite rows record `createdBy` (`convex/blends.ts:142-152,203-204`). Account erasure
delegates memberships to `leaveBlend` (`convex/account.ts:126-132`), which preserves invitations
when another member remains (`convex/blends.ts:84-100`). Preview already falls back to a current
member when the original inviter membership is absent (`:217-225`). Plan 08-04 does not specify
clearing this surviving reference.

**Failure:** the account is erased, but the invite row still contains its stable user ID. This is
an erasure-completeness issue; no claim is made that preview exposes the departed member's name.

**Revision:** reassign surviving invitation attribution to a current member, or make `createdBy`
nullable and clear it on erase/leave. Specify whether the shared invite remains valid, and apply
F08's safe deletion rules. The deleted member identifier is unnecessary for preview behavior.

**Acceptance:** erase an inviter while another member remains. No surviving invite retains the
erased user ID; preview and join follow the documented validity/attribution policy. Exercise the
same case with more than 50 historical invitation rows.

Ordinary library/taste changes during a build remain a daily-snapshot semantics decision. The
publication fence in F01/F02 must cover membership and privacy changes; only add library/taste
revision invalidation if the product promises same-day refresh for those edits.
