# Blend audit: import, web/mobile UX, playback, accessibility, release

Scope: assigned review of F19–F26 and F31–F40, distinguishing current implementation from future plan gaps. Read the Blend master and phases 05, 09, and 10 plans plus source candidates. No code or plan was changed.

## Findings checked

| Finding | Result | Evidence and correction |
|---|---|---|
| F19 | Confirmed, implementation and plan | `packages/shared/importPlan.ts:21,59` measures `JSON.stringify(...).length` and checks `CHUNK_JSON_MAX`; `apps/web/src/lib/api.ts:378` adds the actual `sentAt`. UTF-8 text can exceed the 32 KB API body limit while remaining under the 28,000-character cap. Retain the byte-based chunk proposal, including envelope and an explicit individually oversized operation case. |
| F20 | Confirmed, implementation and plan | `apps/web/src/lib/importFile.ts:42-60,68-78` uses synchronous `unzipSync`, caps the compressed archive and each wanted entry, but does not cap aggregate expanded bytes or work. A ZIP with many individually valid wanted entries can still expand excessively. This is a browser-worker memory/availability risk; retain aggregate actual-byte and cancellation/time bounds. |
| F21 | Confirmed, implementation and plan | `apps/web/src/lib/importProgressStore.ts:11-22,38-85` stores match results keyed only by file hash. `ImportState` stores selection/review state only in memory (`apps/web/src/lib/importReducer.ts:22-38`); accepted/manual replacements, planned ops and save receipts are not persisted. Clarify that current “resume” only skips matches after the same file is selected again; it does not resume review or saving safely. |
| F22 | Confirmed, implementation and plan | `packages/shared/importParse.ts:14-25,138-180` models imported playlists by name only. `packages/shared/importPlan.ts:27-29,50` derives IDs from `source:name`; duplicate same-name lists collapse, and renames create different IDs. Keep the identity/re-import policy and repeated-track/order acceptance cases. |
| F23 | Confirmed, implementation and plan | Matching errors carry a preview resume state (`apps/web/src/lib/importReducer.ts:102-104`), but saving errors become `{step:'error', resumable:true}` without a `resume` payload (`:115-121`). The UI shows “Carry on” only when both are present (`apps/web/src/components/import/ImportPage.tsx:284`). Therefore save failures currently have no resume action despite the `COPY.saveFailed` promise at `:28`. No run ID guards stale results. Keep separate matching and saving recovery cases; explicitly make the save failure acceptance test assert a visible usable recovery action. |
| F24 | Confirmed, implementation and plan | `apps/api/src/services/importMatch.ts:122-135` converts provider exceptions to confidence `none`; web persists returned matches (`apps/web/src/components/import/ImportPage.tsx:86-98`). A transient outage can thus be checkpointed as a definitive miss. Preserve the retryable/unavailable outcome. |
| F25 | Confirmed, implementation and plan | `apps/api/src/services/importMatch.ts:81-97,127` uses title/lead/artist overlap and duration for “exact”, but allows “close” despite duration mismatch; cache key omits album/version metadata. `close` begins accepted in the phase 05 reducer contract. Keep ambiguity review and cache-version requirements. |
| F26 | Confirmed as a release gate only | Phase 04 summaries and fixture README identify synthetic fixtures; phase 04-01 is an owner-supplied real-export checkpoint. No actual export was available in this audit. Keep “real Spotify compatibility unverified” as a blocked/manual release claim, not as a demonstrated parser bug. |
| F31 | Confirmed, implementation and plan | `apps/web/src/components/blend/BlendInviteSheet.tsx:39-61` polls full detail every 3 s with `setInterval`; a slow request can overlap the next tick. Close/unmount clears the timer but cannot abort the in-flight request; errors are silently retried. Retain backoff, one-flight scheduling, cheap status, and terminal invite-state cases. |
| F32 | Needs wording/priority correction | The web Blend page passes playback to the app callback (`apps/web/src/App.tsx:1388`), and `playSong` routes to `connect.playRemote(song, queue)` before local playback (`:1008-1038`). Do not characterize current Blend playback as a local setter bypass. The plan still does not define filtered-row queue tails, play-next/add, rebuild while playing, or remote owner behavior. Keep as a P2 queue-contract and integration-acceptance gap; prove current callback behavior in browser and remote-device tests. Mobile rows use `StreamService.play(songs,index)` (`apps/mobile/src/screens/BlendScreen.tsx:149-168`) and need device proof for the native queue contract. |
| F33 | Confirmed, implementation and plan | `apps/web/src/components/blend/shareCard.ts:14-26,97-129` waits for artwork and `toBlob()` before calling `navigator.share`, then catches every rejection and downloads. Transient activation can expire; cancellation is treated as a download request; null/security failures need defined outcomes. Retain two-step/prepared-share design, `canShare`, cancellation handling, fonts/RTL/long-text cases. |
| F34 | Confirmed, implementation and plan | `apps/web/src/components/blend/BlendPage.tsx:157-161` assigns radio roles but defines no arrow-key/roving-focus behavior. `BlendRing.tsx:51-68` exposes thin pair lines through separate hit targets and provides no linear score list. Import review may contain up to 10,000 tracks. Keep keyboard/screen-reader, zoom, batch announcements and bounded/virtualized review acceptance cases. |
| F35 | Plausible plan gap; keep deployment qualification | The plan defines independently enabled web/API flags and stable reveal keys by ID/day, while groups expand shared membership. The cited old-client/capability behavior is not proven against a released APK here. Frame as a compatibility/rollback gate and specify client capability behavior before widening membership; don’t claim an old-client production failure without release evidence. |
| F36 | Confirmed plan defect, mitigated in current code | Phase `10-01-PLAN.md:69` says `Share.share({ url })`, but React Native documents `url` as iOS-only ([React Native Share](https://reactnative.dev/docs/share)). Both current invite flows include the complete HTTPS link in `message` (`apps/mobile/src/screens/BlendsScreen.tsx:55`, `BlendScreen.tsx:95`), so the current code already avoids the Android URL-field failure. Revise the plan to preserve that behavior and retain physical Android destination-receipt proof; a resolved native share promise does not prove delivery. |
| F37 | Confirmed future-plan risk, not a current mobile importer bug | The mobile Spotify importer is not implemented: current `apps/mobile/src/utils/exportImport.ts:101-141` imports only Allegra backup JSON synchronously with `readAsStringAsync`/`JSON.parse`; phase `10-02-PLAN.md` proposes the new ZIP importer. Keep the expansion/cancellation/URI/low-memory acceptance before that plan ships, but label it planned behavior rather than a regression in a deployed feature. |
| F38 | Confirmed plan gap | Phase `10-03-PLAN.md` covers host/certificate and install state but omits cold/warm launch through auth, account choice, expiry during sign-in and post-acceptance revalidation. No production assetlinks/certificate or device proof was checked. Keep as a release gate; test installed, uninstalled and signed-out journeys with the actual distribution certificate. |
| F39 | Confirmed documentation-state conflict | `.planning/blend/PLAN.md:3` says nothing is built, while `STATE.md`/milestone roadmap and existing source/summaries show phases partially implemented. Reconcile approved plan, local implementation, gates, deployment and manual acceptance before handoff. The broader listed formula/contract drift should retain exact source-of-truth pointers so this stays actionable. |
| F40 | Confirmed verification gap; do not infer that tests are bad | The primary audit reports 138 passing tests plus 10 scratch scenarios, but these do not establish real-export, physical-device, two-account, old-client, or production proof. Preserve behavior-based adversarial acceptance and separate local gates from release/manual gates. `apps/web` source includes tests for reducer/import parsing but not those release journeys. |

## Additional gaps

No distinct high-value product enhancement emerged in this slice beyond E01–E10. The most actionable additional acceptance detail is attached to F23 above: the current save-error state advertises resumability but has no resumable state payload, so test the visible recovery path, not only reducer transitions.

## Verification and limits

- Read-only source/plan audit; no tests or app builds rerun, per the parent instruction to avoid duplicating the initial suite unless new uncertainty required it. The primary report records the initial 138 tests and 10 scratch checks; those results are not independently re-verified here.
- No mobile device, two-account browser, live Convex/Vercel deployment, real Spotify export, Android share-target receipt, or installed release certificate was available for this slice.
- External research: one Firecrawl search returned React Native’s official Share page, cited at F36. No crawl, batch, monitor, install or deployment was run.
- Graft calls saved approximately **322,029 tokens** across this audit turn (sum of the per-call estimates printed by Graft).
