## Additional backend privacy finding

**B-A1 — P2 — Erasure leaves an erased member ID on surviving invite rows.**

- **Current implementation:** invite rows store `createdBy` at creation (`convex/blends.ts:142-152`, `:203-204`). Account erasure delegates each membership to `leaveBlend` (`convex/account.ts:126-132`). When another member remains, `leaveBlend` only deletes the membership and patches the Blend (`convex/blends.ts:84-100`); it neither deletes the surviving invite nor clears/reassigns its `createdBy`. Invites are deleted only when the whole Blend is deleted (`:71-76`). Preview uses the stale ID to look for an inviter membership, then falls back to a current member (`:217-225`), so the former ID is not necessary for behavior.
- **Failure:** a completed account erase can leave the deleted account's stable user ID in a still-live invite row for up to the invite lifetime. This is a bounded retention issue, not a claim that the deleted member's name is shown.
- **Plan gap:** 08-04 specifies removing `blendMembers` and applying leave rules, but does not specify clearing references from surviving invites.
- **Plan change:** on leave/erase, reassign surviving invite attribution to a remaining member or make `createdBy` nullable and remove it. Keep the shared invite valid if that is the chosen product behavior.
- **Acceptance:** erase a member with an unexpired invite in a surviving Blend; the invite still follows the documented validity rule, preview uses a remaining member, and no invite row retains the erased user ID.

## Additional backend retry finding

**B-A2 — P1 — Retrying Blend creation after a lost response creates a second Blend.**

- **Current implementation:** `apps/web/src/lib/api.ts:523-524` sends only name and consent; `apps/api/src/routes/blends.ts:112-122` always invokes `create`; `convex/blends.ts:124-152` inserts a new Blend, membership and invite for every valid call. There is no request/idempotency key or lookup for a pending creation.
- **Failure:** if Convex commits but the HTTP response is lost, a user retry creates a second Blend and second invite. The user can hit the 20-Blend limit early, and a friend may join the abandoned link. This is a response-loss/retry issue, not a concurrent double-click claim; the client can disable a button while a request is active and still cannot know whether a timed-out request committed.
- **Plan gap:** B2/B3 specify create's mutations and response but no idempotent retry contract.
- **Plan change:** accept a client-generated operation key for creation and persist a unique per-account operation result in Convex; replay the original response on retry. Bound/expire operation records so this stays within the existing Convex data model.
- **Acceptance:** commit create, simulate dropping the 201, retry the exact operation key sequentially and concurrently, and verify one Blend/member/invite exists and the same result is returned; a different key creates a distinct Blend.

**Other retry/input scope:** `join` already replays safely because `convex/blends.ts:238-239` returns for existing membership. An invite-regeneration retry can rotate again, but the caller can retrieve the current live code through the non-regenerating invite call; this is lower consequence than creation duplication. The current design intentionally rebuilds on the daily boundary or membership staleness (`08-03-PLAN.md:89-103`), so I did not classify ordinary library/taste changes during a daily build as a defect. The proposed publication fence must cover membership and learning revocation; if the product later promises same-day refresh on likes/listens, then library/taste revisions and their cross-query snapshot semantics need a separate contract.
